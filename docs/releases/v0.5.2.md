# v0.5.2 — Camera snapshots and Bluetooth diagnostics

This release includes the CameraCapture changes from unreleased version 0.5.1,
plus BLE command support and clearer monitoring messages. The previous public
release was 0.5.0.

## What's new

- **Camera snapshots.** The CameraCapture command returns a JPEG with its MIME
  type, length and SHA-256 using the existing signed command reply. It supports
  direct HTTP(S) JPEG, ONVIF Media1 discovery and authenticated RTSP over TCP
  carrying RTP/JPEG. Tapo C211 native JPEG capture is supported through its
  `/stream8` profile.
- **Bluetooth diagnostic commands.** BleBroadcast decodes a selected device's
  retained advertisements; BleBroadcastListen reports raw advertisements from
  the shared completed scan snapshot. Both reuse the continuous passive scanner
  and existing command authentication.
- **Clearer BLE monitoring messages.** The message shows the selected reading
  recorded for that monitoring execution, for example `Temperature: 10 °C`,
  matching the measurement encoded in PingInfo. It no longer calls that reading
  the last observed value or includes the complete decoded advertisement.
- **Shared BLE parsing and crypto.** Monitoring and diagnostic commands use the
  same payload selection, key parsing and decryption helpers.

## Limits and updating existing devices

CameraCapture preserves the camera's native dimensions and limits JPEGs to
64 KiB. H264/H265, resizing, redirects, cross-host advertised camera URLs and
insecure HTTPS are unsupported. BLE commands inspect already collected data;
they do not start a second scan or wait for new advertisements. Reports are
limited to 48 KiB and 256 lines, with explicit failure on overflow.

OTA retains enrollment, Wi-Fi settings and monitor configuration. Existing
DisabledCommands restrictions are also retained. Enabling CameraCapture or the
BLE commands on an enrolled device may require a deliberate configuration and
capability-registration update. Registration rotates AuthKey: use the coordinated
device workflow that verifies and installs its replacement.

See the [command documentation](https://github.com/Mungert69/NetworkMonitorProcessorAgentEmbedded/blob/v0.5.2/docs/command-processor-port-notes.md)
for arguments, supported camera transports and BLE command limits.

## Validation

All 44 native tests passed with AddressSanitizer and UndefinedBehaviorSanitizer
across the full run and a retry of the state-adapter target, which was initially
unavailable during a rebuild. Tooling checks passed: 53 tests, one skipped.
The signed 0.5.2 firmware built successfully and its RSA signature was verified
against the existing signing key. The application uses 0x251000 bytes, leaving
61% of each 6 MiB OTA slot free.

The unreleased 0.5.1 camera validation included real ESP-IDF emulator transport
checks for HTTP Basic/Digest, SOAP discovery, body bounds, cancellation and
RTSP/TCP JPEG reconstruction. An authenticated C211 host capture was independently
decoded, and an app-only USB board update preserved enrollment and monitoring
state. Those are prior 0.5.1 results, not new 0.5.2 hardware validation. Signed
camera replies through the live backend, physical BLE command execution and
HTTPS OTA lifecycle/rollback remain unverified for this release.

## Downloads and installation

- Use `networkmonitor-esp32-s3-0.5.2-<sha256>.bin` for OTA on an enrolled device.
- Use `networkmonitor-esp32-s3-live-factory-0.5.2.bin` only for first installation
  on ESP32-S3 hardware with 16 MB flash and 8 MB PSRAM. Factory installation
  replaces device settings and requires Wi-Fi setup and enrollment.
  **Do not use the factory image for OTA.**
- Verify downloads using the attached `SHA256SUMS.txt`.

Project source is GPL-3.0-only; dependencies retain their own licenses. Matching
source is available at the immutable [v0.5.2 tag](https://github.com/Mungert69/NetworkMonitorProcessorAgentEmbedded/tree/v0.5.2).
Clone with `--recurse-submodules` to include pinned dependencies; GitHub's automatic
source archives omit submodule contents. The attached CycloneDX SBOM and
third-party notices identify the included components. Release images contain no
device credentials, enrolled flash or private signing keys.
